PROTOCOL PHASES SIMULATED:
--------------------------

Phase 1: CC Metric Collection
  - CC collects cluster internal metrics (delay, loss, queue)
  - CC measures inter-cluster link metrics
  - Shows collected data from all clusters

Phase 2: CC→AC Metric Reporting (INTERCLUSTER_LINK_METRICS)
  - Each CC sends INTERCLUSTER_LINK_METRICS message to AC
  - Message includes: cluster_id, link metrics (latency, loss)
  - AC receives and stores all inter-cluster link metrics
  - Matches protocol definition from message.proto

Phase 3: Cross-Cluster Flow Request (FLOW_REQUEST)
  - Host initiates cross-cluster communication
  - Source CC detects traffic and sends FLOW_REQUEST to AC
  - Message includes: src_cluster, dst_cluster, match_fields
  - Matches protocol definition from message.proto

Phase 4: AC Path Computation (FLOW_REPLY)
  - AC runs routing algorithm (Baseline or Cluster-Aware)
  - AC computes cluster-level path
  - AC sends FLOW_REPLY with path and segments
  - Message includes: path[], segments[], match_fields
  - Matches protocol definition from message.proto

Phase 5: Flow Installation
  - Each CC in path installs forwarding flows
  - Cross-cluster routing path established
  - Traffic can flow end-to-end

PROTOCOL MESSAGES:
-----------------

1. INTERCLUSTER_LINK_METRICS (CC→AC)
   Structure:
   {
     cluster_id: int
     num_links: int
     metrics: [
       {link_key, latency_ms, loss_ratio}
     ]
   }

2. FLOW_REQUEST (CC→AC)
   Structure:
   {
     src_cluster: int
     dst_cluster: int
     match_fields: {dst_ip, src_ip}
   }

3. FLOW_REPLY (AC→CC)
   Structure:
   {
     path: [cluster_ids]
     num_hops: int
     segments: [
       {cluster_id, ingress, egress}
     ]
     match_fields: {dst_ip, src_ip}
   }
