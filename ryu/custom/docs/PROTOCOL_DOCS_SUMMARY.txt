8种消息类型完整说明
======================================================================

┌──────────────────────────────────────────────────────────────┐
│ 1. HELLO - 握手消息                                           │
├──────────────────────────────────────────────────────────────┤
│ 方向: 双向 (CC ↔ AC)                                          │
│ 用途: 建立连接时的初始握手，交换身份和版本信息                │
│ 字段: node_id (节点标识), version (协议版本)                   │
│ 场景: 连接建立、版本协商、身份验证基础                         │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 2. TOPOLOGY_UPDATE - 拓扑更新消息                             │
├──────────────────────────────────────────────────────────────┤
│ 方向: CC → AC                                                  │
│ 用途: CC向AC报告本集群的边界拓扑信息                           │
│ 字段: cluster_id, boundary_switches, boundaries (结构化)       │
│ 场景: CC启动、检测到边界变化、定期更新                         │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 3. INTERCLUSTER_LINK_UPDATE - 跨集群链路发现                  │
├──────────────────────────────────────────────────────────────┤
│ 方向: CC → AC                                                  │
│ 用途: CC通过LLDP发现跨集群链路后上报                           │
│ 字段: cluster_id, links (switch_id, port_no, link_key)        │
│ 场景: LLDP发现跨集群邻居、链路建立、链路变化                   │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 4. INTERCLUSTER_LINK_METRICS - 链路指标上报                   │
├──────────────────────────────────────────────────────────────┤
│ 方向: CC → AC                                                  │
│ 用途: CC定期向AC上报跨集群链路的性能指标                       │
│ 字段: cluster_id, metrics (latency_ms, load, loss_ratio, bw)  │
│ 场景: 周期性指标上报、用于加权路由决策                         │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 5. FLOW_REQUEST - 跨域流请求                                  │
├──────────────────────────────────────────────────────────────┤
│ 方向: CC → AC                                                  │
│ 用途: CC检测到跨集群流量时，向AC请求路由路径                   │
│ 字段: src_cluster, dst_cluster, match_fields (src_ip, dst_ip) │
│ 场景: 主机发起跨集群通信、首包触发                             │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 6. FLOW_REPLY - 路由路径应答                                  │
├──────────────────────────────────────────────────────────────┤
│ 方向: AC → CC                                                  │
│ 用途: AC计算路径后向相关CC下发路由指令                         │
│ 字段: path (集群序列), match_fields, segments (详细段信息)     │
│ 场景: 响应FLOW_REQUEST、下发路径、指导流表安装                 │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 7. KEEPALIVE - 心跳消息                                       │
├──────────────────────────────────────────────────────────────┤
│ 方向: CC → AC                                                  │
│ 用途: 维持连接活跃状态，检测对端故障                           │
│ 字段: ts_ms (时间戳)                                           │
│ 场景: 周期性心跳（10秒）、故障检测（30秒超时）                 │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 8. ERROR - 错误消息                                           │
├──────────────────────────────────────────────────────────────┤
│ 方向: 双向 (CC ↔ AC)                                          │
│ 用途: 报告协议处理错误或异常情况                               │
│ 字段: code (错误码), reason (错误原因描述)                     │
│ 场景: 版本不匹配、资源冲突、请求错误、系统故障                 │
└──────────────────────────────────────────────────────────────┘

4个核心协议工作流程
======================================================================

【流程1】系统初始化流程
----------------------------------------------------------------------
步骤1: AC启动
       → 监听TCP端口 (如10000)
       → 初始化SyncProtocol
       → 初始化ThreadSafeStateManager
       → 启动心跳监控线程

步骤2: CC启动
       → 加载本集群配置
       → 连接到AC
       → 发送HELLO消息

步骤3: 握手完成
       → AC接收HELLO，记录CC信息
       → AC发送HELLO应答
       → 连接建立成功

步骤4: 拓扑初始化
       → CC启动LLDP拓扑发现
       → 检测边界端口
       → 发送TOPOLOGY_UPDATE到AC

【流程2】跨集群链路发现流程（基于LLDP）
----------------------------------------------------------------------
阶段1: LLDP发送
       CC-1在所有端口发送LLDP
       → LLDP包含: chassis_id, port_id, TTL
       → 使用自定义TLV携带cluster_id

阶段2: LLDP接收与识别
       CC-2接收LLDP包
       → 解析chassis_id和cluster_id
       → 判断: cluster_id ≠ local_cluster_id
       → 识别为跨集群链路

阶段3: 链路上报
       CC-1和CC-2各自发送INTERCLUSTER_LINK_UPDATE
       → 包含: switch_id, port_no, link_key
       → AC接收两端信息

阶段4: 链路匹配
       AC根据link_key匹配
       → 确认链路两端
       → 更新集群拓扑图: add_edge(C1, C2)
       → 记录链路端点信息

【流程3】跨域路由请求处理流程
----------------------------------------------------------------------
阶段1: 流量触发
       Host h1 → Host h3
       → Packet到达CC-1
       → 查询目标IP：不在本集群
       → 确定目标集群

阶段2: 路径请求
       CC-1发送FLOW_REQUEST到AC
       → src_cluster, dst_cluster
       → match_fields: {src_ip, dst_ip}

阶段3: 路径计算
       AC执行路径计算算法
       → 输入: 集群拓扑图
       → 算法: Dijkstra或加权最短路径
       → 输出: path = [1, 2, 3]

阶段4: 路径下发
       AC发送FLOW_REPLY到CC-1, CC-2, CC-3
       → 每个CC接收路径信息
       → segments包含本地处理所需信息

阶段5: 流表安装
       各CC安装OpenFlow流表
       → CC-1: match → output(border_port to C2)
       → CC-2: match → output(border_port to C3)
       → CC-3: match → output(local_port to h3)

阶段6: 数据转发
       Packet沿路径转发
       h1 → sw1(C1) → sw2(C2) → sw3(C2) → sw4(C3) → h3

【流程4】链路指标上报与加权路由
----------------------------------------------------------------------
阶段1: 指标采集
       CC定期测量跨集群链路性能
       → ICMP探测测量时延
       → 统计流量负载
       → 计算丢包率

阶段2: 指标上报
       CC发送INTERCLUSTER_LINK_METRICS到AC
       → 周期: 5-10秒
       → 指标: latency, load, loss_ratio

阶段3: 指标聚合
       AC接收并存储所有链路指标
       → 更新集群拓扑图的边权重

阶段4: 加权路由
       AC在路径计算时使用指标
       → 边权重 = α×latency + β×load + γ×loss + δ×cluster_cost
       → 运行加权Dijkstra算法
       → 选择代价最小路径

======================================================================
技术实现特点
======================================================================

【特点1】Protocol Buffers序列化
----------------------------------------------------------------------
优势:
✓ 高效的二进制编码，减少网络传输开销
✓ 强类型定义，降低解析错误
✓ 向后兼容性，便于协议演进
✓ 跨语言支持，便于异构系统集成

使用: protoc --python_out=. message.proto

【特点2】线程安全设计
----------------------------------------------------------------------
技术:
✓ 细粒度锁 (Fine-grained Locking)
✓ 读写分离 (Read-Write Separation)
✓ 无锁数据结构 (Lock-free Queue)

保证: 多CC并发访问、心跳线程与主线程并发、状态一致性

【特点3】可靠性机制
----------------------------------------------------------------------
机制1: 消息超时与重传
       → track_message() 跟踪消息
       → 设置timeout=10.0秒
       → 超时后重传，最多3次

机制2: 心跳监控
       → 周期发送KEEPALIVE (10秒)
       → 超时检测 (30秒)
       → 触发故障回调

机制3: 请求-应答关联
       → msg_id唯一标识消息
       → corr_id关联请求和应答
       → 匹配后处理应答

【特点4】性能优化
----------------------------------------------------------------------
优化1: 批量操作 (Batch Operations)
       → batch_update_links() 减少锁竞争

优化2: 延迟处理 (Lazy Evaluation)
       → 路径缓存标记为脏
       → 查询时才重新计算

优化3: 消息优先级队列 (Priority Queue)
       → FLOW_REQUEST高优先级
       → KEEPALIVE低优先级
       → 公平调度避免饥饿

实际应用案例
======================================================================

【案例1】三集群场景 (C1 ↔ C2 ↔ C3)
----------------------------------------------------------------------
拓扑: Cluster1 ←→ Cluster2 ←→ Cluster3
跨域通信: h1(10.10.0.10) → h3(10.30.0.10)

流程:
1. h1 ping h3
2. CC-1发送FLOW_REQUEST(src=1, dst=3)到AC
3. AC计算路径: [1, 2, 3]
4. AC发送FLOW_REPLY给CC-1, CC-2, CC-3
5. 各CC安装流表
6. ping成功，端到端时延: 24.67ms

【案例2】五集群环形拓扑加权路由
----------------------------------------------------------------------
拓扑:     C1 ←→ C2
         ↕       ↕
         C5 ←→ C4 ←→ C3

对比:
基线算法 (hop-count): C1 → C4
  → 1跳
  → 时延: 76.31ms
  → 丢包: 15%

加权算法 (cluster-aware): C1 → C5 → C4
  → 2跳
  → 时延: 64.02ms
  → 丢包: 1.2%
  → 改善: 时延-16%, 丢包-92%
